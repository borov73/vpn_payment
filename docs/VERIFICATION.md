aiosqlite 0.22.1. Runtime- и dev-зависимости зафиксированы отдельно.

После исправлений финального аудита на macOS: **184 passed, 2 skipped**;

Ruff, форматирование, компиляция исходников и `pip check` проходят.


Тесты используют только mock API, синтетические адреса и временные базы.
Персональные адреса, хеши и подробности реальных платежей в отчёт не включены.

## Исправления по итогам аудита

- Незавершённая перепроверка сохраняется в SQLite и повторяется после восстановления
  RPC и перезапуска. Ошибку нельзя забыть из-за возраста старого платежа.
- При повторном обходе применяется та же граница отключения получателя, что при
  импорте истории. Ранее записанный платёж не выпадает из учёта после смены реквизитов.
- Корректировки задаются в EUR. Предпросмотр правил и сумм считает реальный сохранённый
  ledger; значения, выводящие даты за поддерживаемые границы, отклоняются до записи.
- Адреса и начало поиска обязательны в приватном `.env`; личных значений по умолчанию
  в исходниках и образце нет. Публичные тесты используют синтетические примеры.
- Инструкции описывают подключение существующей установки к Git и явную проверку
  целостности выбранной резервной копии перед восстановлением.

Дополнительно проверены деньги Decimal/wei, границы периодов, отрицательные остатки,
поздние и будущие платежи, оба исторических получателя, успешные receipts, подтверждения,
nonce-поиск, дубли, отдельные курсоры, пропуски курсов и резервная биржа, неизменность
исходной EUR-оценки, корректировки с аудитом, миграции без потери данных, read-only
status/backup, блокировка одного процесса и корректное завершение.

## Уведомления и резервное копирование

Mock-проверки покрывают напоминания за 7/3/1 день, предоплату, уведомление о новом
подтверждённом оценённом платеже, отсутствие повторов после рестарта, сохранение
Telegram retry_after и блокировку точных напоминаний при неполных данных.

Backup использует SQLite backup API и `integrity_check`. После успешной новой копии
удаляются только автоматические копии старше 5 суток и их обычные файлы WAL/SHM.
Ручные копии, ссылки и подкаталоги сохраняются. Ошибка backup не запускает очистку.
Рабочая база и её полная история под ротацию не попадают.

## Реальные read-only проверки и пределы

На Ubuntu 24.04 VPS подтверждены работа systemd-сервиса от отдельного пользователя,
включённый автозапуск, штатный перезапуск, фоновая синхронизация и Telegram polling.
Base RPC возвращает chain ID 8453, блоки, receipts и исторические nonce.
Исторический ETH/EUR доступен через CCXT. Рабочая база и резервные копии проходят
`integrity_check`; исходные сохранённые EUR-оценки не переоцениваются.

После установки исправлений проверены журнал именно нового systemd-процесса,
начало polling и успешная фоновая синхронизация без ошибок. Таблицы платежей,
котировок, корректировок, правил, их аудита и уведомлений совпали с состоянием
до обновления. Перед заменой кода сделан backup; обновлённый backup-сервис также
выполнен успешно, целостность новой копии проверена.

Конфигурация и база имеют приватные права. Входящие сервисы ограничены SSH;
SSH требует авторизации владельца, бот проверяет Telegram User ID и private chat.
Публикация кода не публикует VPS, конфигурацию, базы или учётные данные.

Фактическая доставка уведомления о новом реальном платеже и порогового напоминания
ещё не проверялась: новые переводы ради теста не отправлялись. Полная перезагрузка
VPS не выполнялась. У неопределённого ответа Telegram есть осознанный компромисс:
уведомление может потеряться, поскольку слепой повтор способен создать дубль.

Копии находятся на том же VPS — важные копии нужно периодически переносить отдельно.
Проверки публикации: GitHub Actions для отправленного коммита и статус его GPG-подписи
Verified. История запусков доступна во вкладке Actions репозитория. Подключение
существующей установки VPS к Git описано в deploy/README.md; авторские ключи для
чтения публичного репозитория на сервер не копируются.
