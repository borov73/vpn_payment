# Расчёты и обслуживание

## Старый и новый адреса

`RECIPIENT_ADDRESSES` содержит все адреса провайдера для исторического учёта:
старые и действующие. Личные реквизиты указываются только в приватном `.env`.

`ACTIVE_RECIPIENT_ADDRESSES` содержит **только действующий адрес**. Новые платежи
мониторятся только на него. При первой синхронизации обновлённой версии сохраняется
блок прекращения учёта новых переводов на старый адрес. Это техническая граница
нашего мониторинга, а не предположение о дате смены реквизитов провайдером.
Повторная загрузка истории не добавит более поздние платежи на выведенный адрес;
ранее сохранённые платежи и их оценки остаются в учёте.

Для следующей смены реквизитов добавьте адрес в общий список и замените активный
список, затем перезапустите бота. Старые адреса из общего списка не удаляйте.
Адреса проверяются и нормализуются в EIP-55; активные должны входить в общий список.

## История native ETH через RPC

Стандартный JSON-RPC не выдаёт универсальный список переводов кошелька. Здесь
используется исходящий nonce внешнего EOA-кошелька:

1. Двоичный поиск timestamps определяет начало настроенного диапазона.
2. Одинаковые nonce на границах позволяют пропустить диапазон без исходящей активности.
3. Двоичный поиск находит блок изменения nonce; читаются его полные транзакции.
4. Проверяются отправитель, получатель, положительный `value`, успешный receipt,
   канонический блок и глубина подтверждений. Газ не входит в оплату.
5. Платёж сохраняется до продвижения позиции мониторинга.

Это поиск по активности отправителя, без сканирования Base от genesis и без
использования `eth_getLogs` для обычных ETH-переводов. CCXT в поиске переводов не участвует.
Etherscan и индексатор не используются.

История и текущий мониторинг имеют отдельные позиции. Ошибка исторического состояния
не останавливает независимый live-поиск. Pending и недавние платежи перепроверяются;
старые подтверждённые платежи защищены каноническими контрольными блоками диапазонов.
При обнаружении реорганизации диапазон проверяется заново. Незавершённая полная
проверка сохраняется в SQLite и повторяется после сбоя или перезапуска до успеха.
Ошибка отдельной перепроверки приостанавливает точные напоминания, но не блокирует
независимый поиск новых платежей. 64 L2-подтверждения — выбранный порог, не L1-финальность.

Покрытие относится только к настроенному диапазону, отправителю и top-level native
ETH. Contract wallets, internal transfers, WETH, ERC-20 и платежи через посредников
не входят в поиск. Изменение nonce само по себе не считается платежом.

Если исторические nonce недоступны, восстановите известные платежи вручную:

```sh
python -m vpn_payment import-hashes 0xПОЛНЫЙ_ХЕШ
python -m vpn_payment sync --hash-file var/payment_hashes.txt
```

Нужны настоящие хеши: `0x` и 64 hex-символа. Каждый импорт проверяется через RPC.
Слишком молодой mined-платёж ожидает подтверждений; транзакцию без блока импортируйте
позднее. Импорт отдельных хешей не доказывает полноту истории.

Резерв для RPC без исторических nonce: `HISTORY_MODE=manual`, `MONITOR_MODE=blocks`.
Он читает только новые блоки после сохранённого начального блока, порциями; нагрузка
значительно выше. Если не успевает за сетью, выберите подходящий archive RPC.
Для напоминаний по вручную восстановленной истории подтвердите её учёт служебной
командой из следующего раздела.

## Расчёт и служебные изменения

Каждые 30 × 24 часа от начала начисляется полная стоимость периода. Посуточного
продления нет. Остаток переносится; недостаток становится отрицательным расчётным
балансом, который покрывается последующими платежами. Это не подтверждённый долг
провайдеру. Будущие платежи исключаются из расчёта на прошлую дату.

`баланс = эффективные EUR-платежи − стоимость начатых периодов`.

Оплаченные вперёд полные периоды отодвигают дату необходимого пополнения.
Условный пример: внесено 18 EUR, начислено 12 EUR, баланс 6 EUR. Ближайшее
списание 4 EUR обеспечено; после него останется 2 EUR. Для следующего полного
периода нужно будет добавить ещё 2 EUR.

Начальная цена, длительность, дата и уведомления из `.env` применяются только при
создании базы. Затем источник правил — SQLite. Если дата неизвестна, она предлагается
по первому платежу как предварительная; точные напоминания ждут подтверждения.

Административных кнопок в Telegram нет. Редкие исправления выполняются из CLI
при остановленном боте. Сначала команда показывает предлагаемые изменения:

```sh
python -m vpn_payment configure --start 2026-01-01T00:00:00Z --price 4.00 --period-days 30
```

Дата в примере условная — укажите своё расчётное начало. Предпросмотр показывает
итоговый баланс и дату пополнения по сохранённым платежам; неподдерживаемые даты
отклоняются до записи. Повтор с `--apply` явно подтверждает запись. Изменение правил пересчитывает всю
историю модели. Перед записью автоматически создаётся приватный backup, изменения
аудируются. Аналогично доступны `--notifications on` и `--notifications off`.

После ручного восстановления можно принять известные платежи за основу напоминаний:

```sh
python -m vpn_payment configure --acknowledge-history
python -m vpn_payment configure --acknowledge-history --apply
```

Это подтверждение не делает историю полной и не отключает проверку свежести мониторинга.

Корректировка конкретной EUR-оценки с сохранением исходного курса и причиной:

```sh
python -m vpn_payment adjust 0xПОЛНЫЙ_ХЕШ 5.00 --reason "Уточнение учёта"
```

Сумма задаётся **в евро**: `5.00` означает 5 EUR, а `500` — 500 EUR.
Предпросмотр проверяет итоговый расчёт. После проверки повторите с `--apply`. Значение `auto` вместо суммы возвращает
исходную рыночную оценку, сохраняя журнал корректировок. Старая база с `prepaid`
не переинтерпретируется автоматически: переход требует явного `configure --start ... --apply`.

## Исторический ETH/EUR

Публичные market-data CCXT: Bitstamp, затем Coinbase Exchange; прямая spot-пара
ETH/EUR. Используется OPEN **закрытой минутной свечи, содержащей timestamp блока**.
Проверяются точная минута, положительная конечная цена и наличие торгов.

Короткое историческое окно запрашивается с rate limits и ограниченными повторами.
Текущая цена, другая минута и свеча без сделок не подставляются. Если оба источника
не подходят, EUR остаётся неизвестным, оценка повторяется, точные напоминания ждут.
Kraken не используется: его OHLC-история ограничена последними 720 свечами.

Wei — целые числа, ETH/цена/произведение — Decimal с точностью 60 знаков. EUR
округляется один раз на платёж до цента, ROUND_HALF_UP. Сохраняются источник,
свеча, цена, raw EUR, исходная оценка и отдельные корректировки. Исторический
курс не обновляется вслед за рынком.

## Уведомления и хранение

Проверка переводов — раз в 15 минут, напоминаний — раз в минуту. О пополнении бот
сообщает после подтверждений и появления исторического EUR. Первоначальная история
не рассылается как новые платежи. Напоминания 7/3/1 учитывают предоплату; после
пополнения срок пересчитывается. Пропущенные старые пороги не рассылаются пачкой.
Даты в Telegram — Москва, в базе — UTC. В карточке тарифа только `4,00 € / 30 дней`.

Ключ уведомления записывается до отправки. Перезапуск не создаёт дублей. После явного
Telegram `retry_after` задержка сохраняется и отправка повторяется по сроку. При
тайм-ауте с неизвестным результатом или аварии между записью и отправкой повторов
нет: сообщение может быть потеряно. Атомарно объединить Telegram и SQLite невозможно.

SQLite хранит платежи, котировки, корректировки, правила и их аудит, позиции проверки
и уведомления. Баланс вычисляется заново из этих данных. Схема v3 добавляет срок
повтора уведомлений. Перед обновлением старой схемы создаётся backup `*-before-v3-*`;
история платежей, настройки и ключи уведомлений сохраняются. Старые неиспользуемые
таблицы существующей базы не удаляются. Не запускайте старую версию поверх схемы v3.

```sh
python -m vpn_payment backup
python -m vpn_payment backup --output backups/manual.sqlite3
```

Backup работает только с существующей базой, не создаёт и не обновляет её схему,
учитывает WAL и проверяет `integrity_check`. Существующий файл копии не перезаписывается.
На VPS ежедневный таймер хранит автоматические копии за последние **5 суток**:
после успешного backup удаляются более старые автоматические файлы. Ручные копии
перед обновлениями и рабочая база не удаляются. Backup содержит всю SQLite:
платежи, исходные курсы, корректировки, правила, позиции мониторинга и журнал
уведомлений. Код и `.env` в него не входят. Нужные копии периодически переносите
за пределы VPS.
